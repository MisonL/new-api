# CR-EMPTY-REPLY-218-224-2026-11-02

## 1. 结论摘要

- 218/224 两渠道的「空回复」不是数据显示问题。日志 `content` 列为空是落库策略
  （近 30 天 type=2 共 664451 条 content 为空、仅 398 条有内容，211/220/226 等
  渠道同样如此），不能作为空回复的证据；真正的信号是 `completion_tokens = 0`。
- 空回复的真实形态是：上游长时间不出首帧，随后在吐出第一帧后立刻断流，客户端
  拿到 200 与只有生命周期帧的流，正文为空且按 prompt token 计费。
- 代码侧的修复已经存在于本地 `dev`：`00a691d22` 把「首个内容帧前断流」改成可
  重试错误（`relay/common/stream_interrupt.go`），`222876349` 让健康 Claude 流
  按正常结束分类。生产二进制 `4527d7666` 两者都没有，这是空回复仍在生产的
  直接原因。
- 本轮曾考虑再加一条「首帧/停滞超时」，实测数据否决了这个方案：见第 4 节。
- 隔离开发环境已按 HEAD 重建并实测通过；生产部署仍待执行。

## 3. 生产为什么拿不到任何内容还照样计费

两处缺失都在二进制 `4527d7666`（`date=2026-09-08`）里：

- `git cat-file -e 4527d7666:relay/common/stream_interrupt.go` 返回 absent，
  `RetryableUpstreamStreamInterruptedError` 不存在，首帧前断流不会重试。
- `git show 4527d7666:relay/channel/claude/relay-claude.go | grep PreludeRetrySafe`
  零命中，`ContextKeyResponsesStreamPreludeRetrySafe` 从未在 Claude 通路设置。

本地 `dev` 的行为（`relay/channel/claude/relay-claude.go:1342-1359`）：收到
`message_start` 时置 prelude 重试安全标记，收到 `content_block_start` /
`content_block_delta` 时清除；`relay/common/stream_interrupt.go:27-30` 在该标记
为真时即返回可重试错误。因此「只有生命周期帧就断流」的场景在 dev 上会换渠道
重试，而不是补一个 `message_stop` 当成功返回。

14 天窗口内 `upstream_transport_interrupted` 占各渠道总请求的比例：

| 渠道 | 占比 |
| --- | --- |
| 211 | 95.95% |
| 224 | 95.74% |
| 218 | 94.93% |
| 226 | 93.87% |
| 205 | 20.75% |
| 189 | 1.64% |

接近 95% 的占比说明生产把大量健康 Claude 流也判成了中断，正是 `222876349`
要修的分类缺陷；因此该字段在生产日志里不能直接当作真实中断率读。

## 4. 「首帧/停滞超时」方案被实测否决

原设想：给长时间不出字的请求加一条更严格的阈值，让它更早失败并重试。实测
218/224 在 2026-11-01 之后的 ct=0 且 `status = partial` 行，计算
`upstream_total_ms - frt`（首帧到断流的静默时长）：

| 渠道 | 样本 | p10 | p50 | p90 |
| --- | --- | --- | --- | --- |
| 218 | 476 | -1380 ms | -54 ms | 286 ms |
| 224 | 698 | -834 ms | -42 ms | 943 ms |

中位数为负、p90 不足 1 秒，说明这些流是「憋很久拿到首帧后立刻断」，不存在
首帧之后的长时间停滞。等待发生在首字节之前，而那是推理模型正常的排队与思考
延迟（本次直连实测也观察到 26.6 秒首字节）。因此停滞阈值既不能提前发现这批
失败，又会误伤正常的长思考请求，决定不实现。
