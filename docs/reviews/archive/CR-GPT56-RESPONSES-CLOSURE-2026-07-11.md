# GPT-5.6 Responses 修复收口审计

## 审计范围

- 对 `origin/main..HEAD` 的 GPT-5.6 计费、Responses 历史输入、namespace、流式错误和渠道选择改动进行复核。
- 复核正式服务截图中的 `arguments` 字符串与对象双向类型错误。
- 仅在隔离开发环境 `127.0.0.1:3001` 重建和执行真实请求，未升级正式服务。

## 发现与修复

1. 原生 Responses 渠道曾被 namespace 能力预检查错误拒绝。最新逻辑只对 Responses 转 Chat 兼容路径执行能力校验，原生 Responses 请求直接交给上游处理。
2. 单次兼容重试无法处理多个 namespace 字段或连续出现的不同历史格式错误。现改为有限状态重试链，每次只有在请求体发生实际变化后才继续，最多执行 8 次兼容重试。
3. 流式响应已经向客户端写出正常事件后仍可能重放请求，造成两段流拼接。现仅在响应体尚未写出时允许兼容重试，并在重放前重置上一轮流状态。
4. 部分 GPT-5.6 上游要求 `function_call.arguments` 为对象，另一些上游要求字符串。现支持字符串对象与 JSON 对象双向转换，每个方向每个请求最多尝试一次，避免无限往返。
5. Responses SSE 错误事件曾统一映射为 400。现按错误类型映射参数错误、限流、认证、权限和上游服务错误，保留结构化错误内容。
6. 渠道跳过曾依赖英文错误文案。现使用可由 `errors.Is` 判断的哨兵错误，并删除不再使用的 namespace 预扫描和错误构造代码。
7. 部分上游先发送 `response.created`、`response.in_progress`，再返回参数兼容错误。现暂存这类无业务输出的前导事件；错误发生时可安全重试，出现文本或工具输出后仍禁止重放。
8. 正式环境启用了 60 秒 SSE ping。现单纯 ping 不再被误判为模型输出，因此 60 秒后才返回的参数兼容错误仍可内部重试；任何真实模型事件写出后立即关闭重试窗口。
9. namespace tools 仅在渠道明确声明不支持且请求确定走原生 Responses 时跳过。能力未知渠道继续透传，启用自定义工具桥接的 Responses 转 Chat 渠道继续走原兼容性校验。

新增回归场景包括：

- 多个 namespace 历史项按上游索引依次移除。
- 总兼容重试次数达到上限后保留最后一个真实上游错误。
- arguments 从字符串转对象，再从对象转字符串。
- 仅收到流式前导事件时允许重试，写出文本后禁止重放。
- 仅发送 SSE ping、尚无模型事件时允许重试。
- 显式不支持 namespace tools 的原生渠道会被跳过，能力未知渠道不会被误拦截。
- 启用自定义工具桥接的 Responses 转 Chat 渠道不会被 namespace 原生能力判断误伤。
- SSE 限流错误映射为 429，服务端错误映射为 502。
- `response.error` 与裸 `error` 事件使用同一状态码映射矩阵。

## 发布边界

- 正式容器仍运行提交 `15a5dbd6f22d7bc76c0d42437f86c96844e11a46`，本轮新增修复尚未部署。
- 渠道 72、205 的 502 和渠道 150 的 503 属于当前上游可用性问题，不应表述为本地 namespace 或 arguments 修复失败。
- 渠道 150 若要避免“模型看不到 namespace 工具”，必须在渠道能力注册表中明确标记 `supports_namespace_tools=false`，使含 namespace 工具的自动路由跳过该渠道；仅删除历史 namespace 不能恢复当前轮工具能力。
- 正式升级前必须基于本轮最终提交重新构建生产镜像，并重复 build-info、健康接口和错误日志检查。
